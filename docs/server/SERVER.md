# Инфраструктура и эксплуатация — ERP-система

## Назначение

Сервер обеспечивает развёртывание и сопровождение корпоративной
ERP-системы: телеграм-бот для пользователей, фоновые задачи для
обработки данных и реляционная база данных для хранения бизнес-информации.

## Технологический стек

| Компонент | Технология |
|---|---|
| Язык приложения | Python |
| База данных | PostgreSQL |
| Кэш / брокер очередей | Redis |
| Фоновые задачи | Celery (worker + beat) |
| Пользовательский интерфейс | Telegram Bot |
| Изоляция и упаковка | Docker, Docker Compose |
| Управление процессами ОС | systemd |

## Принципы построения

Инфраструктура спроектирована вокруг трёх идей:

1. **Воспроизводимость** — приложение упаковано в контейнеры, поэтому
   окружение одинаково на локальной машине разработчика и на сервере.
   Это исключает проблему «работает у меня, не работает в проде».

2. **Разделение ответственности** — каждый сервис (база данных, кэш, бот,
   воркеры, планировщик) работает в собственном контейнере. Это позволяет
   независимо перезапускать, обновлять и масштабировать компоненты, а сбой
   одной части не роняет систему целиком.

3. **Автоматизация** — все рутинные операции (запуск при загрузке,
   перезапуск при сбоях, резервное копирование) выполняются автоматически,
   без ручного вмешательства. Это снижает человеческий фактор и время реакции.

## Архитектура развёртывания

Приложение состоит из набора контейнеризированных сервисов, описанных
в единой конфигурации:

- **База данных (PostgreSQL)** — источник истины, хранит все бизнес-данные.
  Состояние вынесено в постоянный том, чтобы данные переживали перезапуск
  контейнера.
- **Кэш и брокер (Redis)** — используется как брокер сообщений для
  фоновых задач и как кэш. Ограничение по памяти настроено так, чтобы
  кэш не вытеснял критичные данные и не разрастался бесконечно.
- **Бот** — пользовательский интерфейс. Отвечает на команды и запросы.
- **Воркер фоновых задач** — выполняет долгие операции (отчёты, выгрузки,
  периодические расчёты) асинхронно, не блокируя интерфейс.
- **Планировщик** — запускает фоновые задачи по расписанию.
- **Миграции** — применяются при старте стека и приводят схему базы
  данных к актуальному состоянию до того, как приложение начнёт работать.

Доступ к базе данных извне закрыт: она слушает только внутренний интерфейс,
что соответствует принципу минимально необходимой доступности.

## Управление жизненным циклом

За жизненный цикл стека отвечает процесс-менеджер операционной системы.
Это даёт два ключевых свойства:

- **Автозапуск после перезагрузки.** Сервер, ушедший в ребут или
  перезапустившийся после обновления, самостоятельно поднимает весь стек —
  участие человека не требуется.
- **Самовосстановление.** Контейнеры настроены на автоматический перезапуск
  при падении. Если процесс завершится с ошибкой, он будет поднят заново.

Запуск стека идемпотентен: повторное выполнение команды запуска приводит
систему к целевому состоянию, не создавая дубликатов и не ломая уже
работающие компоненты.

## Стратегия резервного копирования

Резервное копирование построено как автоматический регламентный процесс.

**Что копируется и почему:**
- **База данных** — главный приоритет, так как содержит незаменимые
  бизнес-данные. Снимается полным логическим дампом, который можно
  развернуть на любой совместимой версии СУБД.
- **Конфигурация окружения** — позволяет воспроизвести окружение и
  параметры подключения.

**Как устроен процесс:**
- Запуск происходит ежедневно по расписанию, без участия человека.
- Действует **ротация**: ежедневные копии хранятся неделю, еженедельные —
  месяц. Это баланс между глубиной истории и расходом дискового пространства.
- Процесс журналируется, поэтому в любой момент можно проверить, когда
  выполнялось копирование и чем оно завершилось.

**Восстановление:** предусмотрен регламент возврата данных из снимка —
остановка пишущих сервисов, применение дампа, повторный запуск. Это делает
резервное копирование не формальностью, а рабочим инструментом.

## Наблюдаемость

Чтобы понимать состояние системы и быстро диагностировать проблемы,
настроены два канала наблюдаемости:

- **Логи контейнеров** собираются с ротацией: ограничен максимальный размер
  файла и число хранимых файлов. Это защищает дисковое пространство от
  неконтролируемого роста при активной работе приложения.
- **Внешний мониторинг** осуществляется через агент, который передаёт
  метрики сервера в систему мониторинга. Это позволяет отслеживать
  доступность и ресурсы в реальном времени.

## Регламент обслуживания

Обслуживание сведено к набору стандартных, воспроизводимых операций:

- **Обновление версии**: получение нового кода, пересборка образов и
  перезапуск стека. Контейнерная модель гарантирует, что новая версия
  запускается в идентичном окружении.
- **Контроль состояния**: проверка статуса сервисов и фактического
  состояния контейнеров, просмотр логов.
- **Контроль ресурсов**: периодическая проверка свободного места и
  занимаемого объёма данными и снимками.
- **Проверка резервных копий**: регулярная верификация, что снимки
  создаются и пригодны к восстановлению.

## Итог

Инфраструктура реализует полный цикл сопровождения приложения:
изолированное и воспроизводимое развёртывание, автоматический запуск и
самовосстановление, защиту данных через регламентное резервное копирование,
наблюдаемость и документированный регламент обслуживания. Такое построение
делает систему устойчивой к сбоям и предсказуемой в эксплуатации.
